## 2. What the prototype proves

The consensus prototype proves deterministic quorum-record generation, epoch-state record generation, finality evaluation, and fork-resolution selection.

Across Phases 444-446, the current runtime tranche demonstrates:
- deterministic quorum-record serialization and digesting,
- deterministic epoch-state record generation with explicit threshold input,
- deterministic finality evaluation from the same quorum inputs,
- deterministic fork-resolution selection using a stable lexicographic state-digest rule,
- bounded local harness integration over the existing `PeerManager` JSON payload path.

The current tranche does not yet prove production-ready distributed finality. It proves that the constitutional/runtime seam for `CDL-051` is coherent enough to benchmark, audit, and extend.

## 4. Failure modes and edge cases

The current conflict label conflates true competing-threshold forks with multi-candidate no-qualifier states; a future phase may need an explicit undecided or insufficient_votes distinction.

Observed or explicit edge cases in the current tranche:
- missing or invalid `quorum_threshold` input is a deterministic validation failure rather than an implicit default path,
- zero or negative `vote_weight` is a deterministic validation failure,
- duplicate `block_hash` values aggregate by block hash rather than being deduplicated,
- mismatched `epoch_index` values across quorum records or epoch-state candidates are deterministic validation failures,
- fork resolution rejects insufficient or non-conflicting candidate sets.

This leaves one semantic ambiguity: the current `conflict` label is still doing double duty for both an actual unresolved fork and a not-yet-qualified multi-candidate state.

## 5. Missing measurements

No multi-validator or multi-process consensus measurement exists yet; that remains future work outside Phase 447.

The Phase-446 bridge exercise was intentionally bounded to a local JSON payload path with a deterministic sender stub. That is valid tranche evidence, but it is not equivalent to a degraded-network, multi-process, or adversarial transport exercise.

Still-missing evidence includes:
- multi-validator timing under independent processes,
- degraded-network behavior under dropped, delayed, or reordered delivery,
- broader transport realism beyond the bounded `PeerManager` exercise,
- concentration-sensitive behavior once cluster membership is available to the finality path.

## 6. Unresolved assumptions

The Phase 445 flat-aggregate finality evaluator does not enforce the CDL-V3 cluster diversity floor; diversity_floor_runtime.py is not called during finality evaluation. Enforcing the CDL-V3 distinct_cluster_floor and max_cluster_share_ceiling in the finality pipeline is a future constitutional obligation before production finality.

The current quorum-record schema does not carry cluster_id or equivalent cluster-membership metadata; enforcing the CDL-V3 distinct_cluster_floor and max_cluster_share_ceiling requires both a quorum-record schema extension and a two-gate finality evaluation change in a future phase.

The 7+1 epistemic panel for knowledge-claim evaluation and the CDL-051 epoch-finality quorum are architecturally distinct quorum types and must not be conflated.

The epistemic finality claims model (agents filing epoch_finality_attestation knowledge nodes evaluated by 7+1 panels with ECU and reputation staking) is a future architectural lane building on CDL-051, not replacing it. A full design proposal is planned as ADR-0021 after Phase 447 completes, using this findings memo and session transcript as primary inputs.

Unresolved assumptions that remain live after this phase:
- the production finality path still needs an explicit design decision on whether diversity-floor enforcement is constitutional inheritance carried directly into `CDL-051` runtime or requires a separate amendment/clarification phase,
- the knowledge-claim evaluation lane and the epoch-finality lane may share terminology around quorum and independence, but they should not share runtime semantics by default,
- the future ADR-0021 lane must be treated as additive architecture work rather than a retroactive reinterpretation of the current `CDL-051` prototype.

## 7. Adversarial regression guards added

Phase 447 adds regression coverage around the concrete edge cases exposed by the runtime tranche:
- missing and invalid `quorum_threshold` handling,
- zero and negative vote-weight rejection,
- duplicate-block-hash aggregation behavior,
- fork-resolution epoch mismatch rejection,
- fork-resolution insufficient-candidate rejection,
- commit-boundary non-mutation enforcement for the findings lane.

These guards do not close the deeper distributed-measurement or diversity-floor gaps. They close the immediate regression boundary for the current single-process prototype and make the remaining open questions explicit for the next architectural lane.
