## §3 - CDL Territory Conflict Check

No CDL row was found that directly ratifies `SufficiencyClaim`,
`ExecutableStarMap`, `TranslationPassport`, or `TensorPayloadDescriptor`.
There is nevertheless substantial adjacent authority, so the result is
"unoccupied direct term, occupied neighboring territory," not "no conflict."

| Authority | Actual scope | Consequence for this lane |
|---|---|---|
| CDL-037 | Executable descriptors and sandbox constraints | Governs executable behavior if a recipe becomes executable; a sufficiency claim cannot bypass its capability/effect boundary. |
| CDL-076 | Truth-primitive announcement gossip | May disseminate accepted truth-primitive records; it is not star-map governance and does not authorize new types. |
| CDL-077 | WANT-HAVE/WANT-BLOCK retrieval | Relevant to content-addressed evidence retrieval; retrieval does not establish authority or sufficiency. |
| CDL-079 | Bootstrap distribution | Relevant to bootstrap delivery, not operation semantics. |
| CDL-080 | N-gram `star.map` route index as the L3 routing layer | May help discover records; it does not define `ExecutableStarMap` execution semantics. |
| ADR-0033 | Published navigation results as first-class `star_map` epistemic nodes | Adjacent to navigation and publication, but not authority for executable recipes. |
| ADR-0030 | Node embedding substrate and content typing | Constrains how content is represented and typed. |
| ADR-0035 and CDL-097 | Homoiconic type-definition architecture and ratified type-registry authority | Any new governed type must follow this authority. The current registry scaffold is default-off and no initial type is inferred from a research name. |
| CDL-083 | Refutation economics and panel/quorum surface | A counterexample can be research evidence without invoking governed refutation economics. Any economic use must satisfy CDL-083 independently. |
| CDL-114 | `source_refs`-based Sybil-diversity attribution | Source diversity is not computational sufficiency; neither implies the other. |

Current `revise.assert` code accepts a bounded operation envelope and validates
its existing content contract. That does not prove an accepted content-type
mapping for `TranslationPassport`, validate a proposed passport payload, or
authorize a submitter. Later work must check operation acceptance, accepted
content type, payload validity, envelope authentication, and submitter authority
as separate gates.

The architecture remains local-first and content-addressed: agents evaluate
their own bounded evidence views and may exchange immutable objects and proofs.
Nothing in this intake authorizes a central checker, registry, policy oracle, or
"latest" service.

## §5 - Open Questions for Phase 1618

1. What exact operation identity, domain, scope, authority view, and freshness
   interval are part of a `SufficiencyClaim` identity?
2. Which observables are preserved: admission, declared output, declared effects,
   or another explicitly bounded tuple?
3. How are expected-valid claims distinguished from refuted claims and unresolved
   evidence without one generic `valid` Boolean?
4. What typed evidence receipt proves exhaustive checking, a separating
   counterexample, or another declared verification method?
5. How are historical claim authenticity, present use eligibility, and
   invocation readiness represented without allowing one to imply another?
6. Is the first schema a local application descriptor, an existing accepted
   payload, or a candidate governed type? The answer must follow the actual
   registry/type audit rather than the proposed name.
7. How are challenge, revision, supersession, and withdrawal represented with
   immutable backward pointers and no mutable `superseded_by` field?
8. What resource bounds apply to domains, evidence lists, proof receipts, nested
   dependencies, and serialized sizes?
9. How does the schema preserve local-first evaluation and avoid a central
   registry, global checker, or permanent cached permission?
