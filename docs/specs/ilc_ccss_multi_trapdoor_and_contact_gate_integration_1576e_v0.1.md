# ILC CCSS Multi-Trapdoor and ContactGate Integration 1576e v0.1

**Phase:** 1576e
**Window:** 1576+
**Date:** 2026-07-22
**Status:** committed
**Sensitivity:** NON-SENSITIVE

## 1. Purpose and Boundary

This document extends the Phase 1576c Graph-Diffused Threshold Envelope design
with a multi-trapdoor model and a ContactGate integration plan. The goal is to
support three future recipient-access patterns:

1. OR trapdoors, where any one authorized key holder can decrypt;
2. threshold trapdoors, where `m` of `D` key holders must cooperate;
3. role-separated trapdoors, where different segments of a logical message are
   decryptable by different roles.

The design also defines a private fit-tag format that lets relays route
envelopes into PrivacyChart cells without learning recipient identity.

This is spec-only. It does not implement runtime code, mutate a CDL or ADR,
clear any activation guard, write to LMDB, activate CCSS, prove anonymity,
claim GPO resistance, or specify a threshold-DKG implementation.

## 3. OR Trapdoor Scheme

An OR trapdoor lets any of `D` designated key holders decrypt independently.
For a share payload `S`, the sender derives one share data key and encapsulates
that data key independently to each holder:

```text
OR_Encap(S, [pk_1, pk_2, ..., pk_D]) ->
  padded_ct_slots[1..D_max] || share_ciphertext
```

Each non-empty ciphertext slot is a hybrid X25519 plus ML-KEM-768 KEM
ciphertext. Empty slots are padded so the relay-visible envelope shape does not
reveal the actual `D`.

Proposed public-RC planning bound:

| Parameter | Value |
| --- | ---: |
| `D_max` | 8 |
| Hybrid ciphertext bytes per OR slot | 1120 |
| Maximum OR slot overhead | 8960 bytes |
| Fixed envelope size | 65536 bytes |

Use cases:

| Use Case | Reason |
| --- | --- |
| Genesis contact ingress | Multiple Genesis operators can independently decrypt incoming messages without requiring a quorum. |
| Operational backup delivery | A primary recipient and backup recipient can both receive high-availability messages. |

Hard rules:

- each OR slot uses independent encapsulation randomness;
- all `D_max` slots are present or padded;
- failed decapsulation by one key holder must not reveal whether another key
  holder can decrypt;
- OR trapdoor metadata must not expose holder identity to relays;
- `D > D_max` is invalid for this profile.

Output token: `or_trapdoor_scheme_defined_phase_1576e`.

## 4. Threshold Trapdoor Scheme

A threshold trapdoor requires `m` of `D` key holders to collaborate before the
message can be decrypted. The future target is:

```text
Threshold_Encap(S, PK_threshold) -> threshold_kem_ciphertext || share_ciphertext
```

Where `PK_threshold` is generated by a ratified distributed-key-generation or
trusted-setup procedure and decryption requires `m` valid partial
decapsulations from distinct key holders.

Use cases:

| Use Case | Reason |
| --- | --- |
| Jury deliberation coordination | Requires multi-party authorization and auditability. |
| High-value governance communication | Reduces single-operator unilateral access. |

Relay-visible overhead is lower than OR for large `D` because only one
threshold KEM ciphertext is visible. The cost is latency and operational
coordination among key holders.

Hard boundaries:

- threshold-DKG is not specified in this phase;
- threshold trapdoors are not suitable for Genesis public contact ingress;
- threshold trapdoor runtime requires a separate cryptographic construction,
  test vectors, and activation authority.

Output token: `threshold_trapdoor_scheme_defined_phase_1576e`.

## 5. Role-Separated Trapdoor

A role-separated trapdoor splits a logical message into fixed-size role
segments. Each segment is independently encapsulated for its intended access
role:

```text
M = M_public || M_addressee || M_audit
```

| Segment | Authorized Reader |
| --- | --- |
| `M_public` | Cell-level or cohort-level role, if such a role is ratified. |
| `M_addressee` | Named recipient capability holder. |
| `M_audit` | Designated auditor or governance role. |

All role segments must be padded to fixed segment sizes or packed into one
fixed-size outer envelope. Variable segment size is forbidden because it leaks
role profile to relays.

Output token: `role_separated_trapdoor_defined_phase_1576e`.

## 6. Private Fit-Tag Format

A fit-tag is a constant-size encrypted/authenticated routing token. Its purpose
is to let a relay place an envelope into the correct PrivacyChart cell without
learning recipient identity or raw capability id.

Canonical logical preimage:

```json
{
  "cell_id": "<PrivacyChart cell id>",
  "epoch_root": "<epoch boundary root>",
  "nonce": "<128-bit random nonce>",
  "fit_tag_version": "ccss_fit_tag_v1"
}
```

Wire shape:

| Field | Relay Visibility | Constraint |
| --- | --- | --- |
| `fit_tag_version` | visible | Fixed string for parser dispatch. |
| `epoch_root_hint` | visible or derivable from batch | Must bind the tag to one epoch. |
| `ciphertext` | visible opaque bytes | Constant size; encrypts `cell_id`, epoch root, nonce, and version. |
| `auth_tag` | visible opaque bytes | Constant size; authenticates the fit-tag. |

Phase 1576b allows relays to operate on cell-level routing surfaces. Therefore
this design does not claim that the relay learns no cell information. The
stronger rule is: the relay may learn or verify the routing cell needed to
batch the envelope, but it must not learn recipient identity, exact agent
identity, raw capability id, trapdoor class, share index, `m`, `n`, or role
structure.

Fit-tag verification model:

1. Relays maintain a bounded set of active cell keys for the current epoch.
2. On envelope receipt, the relay attempts a bounded fit-tag verification
   across active keys or by using a non-identifying cell-key hint.
3. Failure is cheap and aborts before any KEM work.
4. Successful verification assigns the envelope to a cell batch.
5. Fit-tags expire at the epoch boundary and must not be retained beyond the
   current epoch plus the configured replay window.

Hard rules:

- fit-tags are constant size;
- fit-tags are epoch-bound;
- fit-tags are nonce-bound;
- failed fit-tag checks are bounded;
- fit-tags must not be stored beyond the retention window;
- plaintext recipient identity, raw capability id, share index, and trapdoor
  class are forbidden relay-visible fields.

Output token: `private_fit_tag_format_defined_phase_1576e`.

## 7. ContactGate Integration

The existing ContactGate remains a local admission evaluator. It is not a
network firewall and does not become a relay policy engine in this phase.

Future ContactGate policy extension:

| Existing Surface | Extension |
| --- | --- |
| `admission_mode` | Add trapdoor-aware mode values only in a future runtime phase. Current modes remain unchanged. |
| `capability_context_commitment` | Bind to an OR key set commitment, threshold public-key commitment, or role-key-set commitment. |
| `gate_id` | Bind nullifiers and rate accounting to the local gate. |
| `make_contact_gate_nullifier()` | Reuse for local replay/spam accounting with fit-tag nonce commitments. |
| Sanitized verdict | Preserve no-leak invariant; no private keys, raw ids, cell keys, or fit-tags in verdict output. |

Unchanged boundaries:

- ContactGate does not learn PrivacyChart private cell keys.
- ContactGate does not expose allowlists, raw capability ids, invite secrets, or
  private gate rules.
- ContactGate remains local-only until separate public-serving authority exists.

Output token: `contact_gate_integration_defined_phase_1576e`.

## 8. Genesis Ingress Anti-Spam

Genesis public contact should use an OR trapdoor, not a threshold trapdoor, so
that operational backup does not add quorum latency.

Proposed Genesis ingress profile:

| Mechanism | Parameter | Rule |
| --- | --- | --- |
| Proof-of-work or rate token | future calibrated token | Sender attaches a cheap-to-verify anti-spam token before KEM work. |
| Session-count cap | `3` active sessions per estimated source | Excess sessions are rejected or queued locally. |
| Epoch-level volume cap | `k_min * cover_ratio = 1024` envelopes | Overflow queues to the next epoch where policy allows; no expensive processing before cheap checks. |
| Fit-tag required | `fit_tag_version=ccss_fit_tag_v1` | Missing, expired, malformed, or invalid tags are rejected before KEM decapsulation. |

Hard relay rule: Failed anti-spam checks must be bounded and cheap. Relays must
not perform KEM operations on envelopes that fail format or fit-tag checks.

## 9. Future Runtime Gates

Future runtime must remain default-off behind a guard equivalent to:

```text
CCSS_TRAPDOOR_CONTACT_GATE_NOT_ACTIVATED = True
```

Clearance must require:

- fixed envelope serialization tests;
- OR slot padding and `D_max` tests;
- fit-tag constant-size and epoch-expiry tests;
- relay-visible forbidden-field tests;
- ContactGate sanitized-verdict tests;
- cheap-reject-before-KEM tests;
- Genesis ingress rate/PoW token calibration;
- separate cryptographic review for threshold-DKG if threshold trapdoors are
  implemented.

## 10. Required Boundary Sentence

Fit-tag routing hides recipient identity from relays. It does not hide
injection timing from a global passive observer. GPO resistance requires L6
relay shuffle (not yet designed).
